# `src/workflows`

Renders every Nibfin workflow file from one set of templates (#775): the files Core runs
for Nibfin's own repositories and the ones `gh nibfin init` and `upgrade` write into a
user repository. The templates live in `templates/workflows/` at the repository root
and ship in the image at `/opt/nibfin/templates/workflows/`.

## Sets and channels

| Channel | Execution set                                                                                                       | Peer set                            |
| ------- | ------------------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| `own`   | `nibfin-issue`, `nibfin-events`, `nibfin-shared-runner`, `nibfin-job`, `nibfin-runner-request`, `nibfin-e2e-notify` | `nibfin-issue`, `nibfin-e2e-notify` |
| `user`  | `nibfin-issue`, `nibfin-shared-runner`, `nibfin-job`, `nibfin-runner-request`                                       | `nibfin-issue`                      |

- `own`: Nibfin's own repositories. `nibfin-issue.yml` calls Core's
  `nibfin-events.yml` (`./` in the execution repository, `@main` from a peer), and the
  Jobs pull the image by tag (`ghcr.io/taco3064/nibfin:main` for Core) and resolve its
  digest per Job. Steps that run Core's Action call `taco3064/nibfin-core/action@main`
  (R5.6).
- `user`: self-contained files. The events job is inlined into `nibfin-issue.yml`, and
  `nibfin-job.yml` pins the image on one top-level line,
  `  IMAGE_REF: ghcr.io/taco3064/nibfin@sha256:<digest>`, which the collaborator runner
  hook compares with a zero digest. Steps that run Core's Action call
  `taco3064/nibfin-core/action@<commit>`, the full nibfin-core commit the image was built
  from (R5.7, R5.8). User files start with `# Generated by gh nibfin`.

## Command

```
nibfin render-workflows --set execution|peer --channel own|user [--image <ref>]
                        [--commit <sha>] --default-branch <branch>
                        [--workflow <name>]...
```

It prints one JSON object, `{ ".github/workflows/<file>": "<content>", … }` with sorted
keys, and exits 0. It reads only the templates: no environment, token or network.
Invalid input or a template error prints the reason to stderr, nothing to stdout, and
exits 1 (`WORKFLOW_INPUT_INVALID` for input).

- `--image`: required for an execution set. The own channel takes
  `ghcr.io/taco3064/nibfin:<tag>` (Docker's tag grammar), the user channel
  `ghcr.io/taco3064/nibfin@sha256:<64 hex>`. A peer set does not use it, but a given
  image is still checked for its channel.
- `--commit`: required for the user channel (both sets) and not allowed for the own
  channel: the full 40-character lower-case SHA of the nibfin-core commit the image was
  built from, which is the image's `org.opencontainers.image.revision` label. Core
  cannot read it from a digest, so the caller passes both from one release.
- `--default-branch`: non-empty, with no quote or control character.
- `--workflow`: the repository's CI/CD workflow names, each non-blank with no control
  character; sorted by UTF-8 bytes and deduplicated. With none, the `workflow_run`
  trigger is left out.

Values are written as JSON-quoted YAML flow sequences, as gh-nibfin does, so a branch or
workflow name cannot inject YAML or expressions.

## Core's own files

`coreWorkflowRequest` (`core.ts`) holds Core's inputs: the own execution set, image
`ghcr.io/taco3064/nibfin:main`, default branch `main`, workflows `CI` and `Image`.
`npm run render:workflows` writes them to `.github/workflows/`; it overwrites the
rendered names and deletes nothing. `core.test.ts` fails when a committed
`.github/workflows/nibfin-*.yml` differs from its render, or when a rendered file is
missing or an extra one exists. Edit the template, never the rendered file;
`.github/workflows/` changes by hand, so a template change that alters Core's own files
takes the hand route too.

## Template syntax

Templates are `templates/workflows/<file>.yml.eta`; shared parts are
`templates/workflows/fragments/*.eta`. They use [Eta](https://eta.js.org) with
`autoEscape: false`, `autoTrim: false` and a filter that throws on any value that is not
set, so a misspelt or unused value fails instead of printing `undefined`. An unknown
template or fragment throws `EtaFileResolutionError`.

- Values: `<%~ it.<name> %>`, inline, closed with a plain `%>` so the line keeps its
  newline. The values are `imageRepository`, `imageRef` (user), `imageTag` (own),
  `branches`, `workflows`, `eventsToken`, `eventsUses` (own) and `actionUses`; see
  `TemplateData`.
- Conditions and includes sit alone on their line at column 0 and close with `-%>`,
  which removes that line's newline: `<% if (it.channel === "user") { -%>` …
  `<% } -%>`, `<%~ include("/fragments/<name>.eta", it) -%>`.
- Fragments are written at their final indentation and end with a newline.
- `<%` and `%>` appear nowhere else; they do not collide with `${{`, `{{`, `[[` or `$(`.

A block that repeats in one output comes from one fragment: the "Ask a person to act"
step, Core's Action with `command: job-failed` (three times in `nibfin-job.yml`), the
pull steps, the events job (one step, Core's Action with `command: wake`, in
`nibfin-events.yml` and the user `nibfin-issue.yml`) and the header. No formatter
checks the rendered output; the render tests check that it is deterministic, has no
leftover tags or `undefined` and ends with a single newline.
