## Prerequisites

Choose a Public Repository owned by a personal account or an Organization.
Identify a person authorized to install workflows and propose repository changes,
a repository administrator for Runner management, and the executing member.
Repository write access alone does not grant Runner Admin rights.

Review the target repository's branch protections, required checks and applicable
review requirements. Preserve independent technical validation even for a single
human owner. Do not execute untrusted public Issue or fork code on a host with
member logins or administrative credentials.

execution environment with the intended GitHub member and compatible Codex login;
desktop discovery does not transfer desktop credentials.

## Personal repository

<Steps>

1. Confirm the repository is public and identify the intended executing member.
2. Follow the [managed installation walkthrough](../installation/) for CLI
   acquisition, GitHub/Codex sign-in, preview, consent and apply.
3. Review and merge the native installation PR. Let the running command continue
   locally, or resume with the original installation intent after interruption.
4. Read back host adoption, services, Runner online state and configured routing
   separately. Manual registration is for the explicit legacy path.
5. Confirm isolation and Agent readiness before the first eligible Issue below.

</Steps>

## Organization repository

Follow the same [managed walkthrough](../installation/) for an
Organization-owned Public Repository.
Ask an authorized administrator to check workflow permissions, branch rules and
repository Runner policy. Installation write rights and Runner management rights
remain separate.

Unverified: organization installation and policy combinations have not been tested

this onboarding path; use repository-level Runners only.

## First delivery expectations

Enroll the repository through installation and verified host adoption. Create an
Issue containing the authorized work boundary, add `scope` and assign an enrolled
member with a trusted route. Native Blocked by dependencies must be satisfied
before admission; labels or assignment alone do not authorize execution. See
[the lifecycle](../lifecycle/#from-scope-to-closure) and
[wake-up admission](../lifecycle/#wake-ups-and-admission) for current eligibility.

A registered Runner, configured route, online service and observed native dispatch
are different observations. An authorized Issue still proceeds through Shape,
Deliver, independent Accept, applicable CI, final review and native merge.
Only verified lifecycle results establish completed delivery; a consumed relay
receipt or successful local build does not demonstrate this flow.

An offline host delays polling and Jobs; there is no delivery SLA or automatic
cross-member takeover. The relay discovers recent notifications within a bounded
24-hour window and at most three pages of 50 runs per adopted workflow. Recovery
can consume an eligible original before retention expires, but recovery outside
those bounds is not promised. A rerun cannot replace a failed, absent, expired or
consumed original. Confirmed expiry/deletion yields `RELAY_ORIGINAL_EXPIRED`;
incomplete access or timeouts do not prove expiry. Unknown dispatch effects stay
Pending without another POST. Preserve receipts and use
[safe recovery](../security/#recovery-and-single-writer-operation), rather than
removing state or rerunning an expired notification to force delivery.

After host adoption, [project configuration](../project-environment/) can
declare the tools, network access, and Skills that your Jobs need.

Continue with [installation](../installation/) and [CLI usage](../cli/).
