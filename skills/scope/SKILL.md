# Scope approved product requirements into implementable work

Scope turns **specific, approved product outcomes** into an owned, appropriately sized portfolio of **raw implementation Issues**. For each **implementation** Issue, an implementer must be able to tell **what maintained product change to build, which grounded route to use, what makes that change complete, what it needs from others, and how its behavior will be verified**. Verification and release responsibilities are tracked without automatically becoming implementation Issues. Scope decides portfolio boundaries and responsibility; formal Shape investigates one existing Issue and writes its detailed, independently validated delivery contract. Neither stage may turn product experimentation into an implementation substitute or waive the delivery engine's actual gates.

**One development completion boundary per Issue:** Where the project uses a **code-backed self-delivery lifecycle**, an eligible implementation Issue must produce a **substantive, necessary, maintained change** to product code, tests, configuration, workflows, packaging, or user-facing product documentation. Its acceptance includes proportionate reproducible local/unit/process/contract and negative checks. A real host, account login, protected external API, cross-run workflow, deployment, release publication, self-delivery claim, or whole-product E2E is **verification or release responsibility attached to the relevant implementation or existing authorized publishing process**, **not a separate self-delivered implementation Issue**. Do not invent a test fixture, report, no-op commit, manifest, file edit, or other filler solely to satisfy a nonempty Candidate rule. Missing later resources are verification-readiness constraints, not proof that grounded implementation cannot be written. All actual authorization, Candidate/artifact/hook, independent review, CI, merge and closure gates still apply to eligible implementation Issues; they are never waived to accommodate a misclassified task.

**Grounded engineering selection:** Prefer a credible implementation route supported by official provider contracts, relevant existing code or defensible engineering evidence. Record genuine alternatives only when relevant; select one route, its reasons and assumptions. Do not demand a prototype or a target-platform machine before planning independently testable code. Escalate a product decision only for incompatible binding requirements, a known prohibited/unsafe route without a viable alternative, or truly undecided product semantics. A temporary provider error, missing host or unexecuted E2E is not such a contradiction. Do not publish a research/spike, audit, feasibility check, release, or evidence-only task as a code-backed self-delivery Issue. An independently approved non-development outcome may be tracked or executed by the project's separately authorized non-delivery mechanism, but such approval does **not** make it eligible for a code-backed lifecycle.

## Mandatory work-type and feasibility gate (before drafting or publishing)

**Classify first; only then decompose.** Derive the applicable work types and delivery mechanism from current product authority; this Skill must not silently impose a code-backed lifecycle on projects that explicitly authorize a different one. **When the intended lifecycle requires a nonempty maintained Candidate (including AI self-development), every new Issue proposed for that lifecycle must pass all five checks:**

1. **Actual development:** Name the observable product deficiency and the **necessary maintained source outcome** (code, meaningful regression tests, configuration, workflow, packaging, or actual product documentation). Identify the owning repository and likely affected surface. A test-only change qualifies **only when it is itself necessary maintained regression/contract coverage**, not a pretext to record an external verification result. Product documents qualify when the deliverable is real maintained documentation, not a ceremonial evidence report.
2. **No verification/release masquerade:** Distinguish implementation and its routine tests from standalone E2E/security audit, incident diagnosis, live Runner/OS proof, formal Release/Marketplace publication, asset read-back, deployment approval, self-hosting proof, or support certification. These have named accountable owners **within existing acceptance, CI, release, or provider workflows**, without a new self-delivery Issue or execution-enrollment metadata. An ordinary provider tracking Issue may exist outside that lifecycle where authorized; its presence is not execution eligibility.
3. **Grounded route and prerequisites:** Inspect existing implementation and official provider capabilities before writing **"reuse existing"**, **"already supported"**, or **"automatically recoverable"**. Name the concrete current interface/provider source and why it suffices. If it does **not** exist, either explicitly scope a **needed new feature with an approved feasible route and measurable code outcome**, or return the precise affected product decision for authorized replanning. Do not make an absent capability both a prerequisite and the proposed deliverable, or insert a research Issue to conceal the gap.
4. **Supported completion:** Check the **installed** delivery runtime's Candidate and stage rules, not only aspirational product policy. Demonstrate that the proposed meaningful change and associated checks can complete through that runtime. If a valid development task needs a new delivery-engine capability, assign the engine change to a separately authorized implementation boundary; do not make the dependent Issue try to implement the gate needed to start itself. Genuine unresolved safety conditions remain blocked/Pending.
5. **No accidental execution grant:** A draft, normal tracking Issue, verification ledger, release checklist, label, or native dependency is not automatically a deliverable or a work grant. Publish only eligible implementation Issues into a code-backed lifecycle, using actual authorized metadata and a current runtime read-back. When correcting existing protected work, follow its separate lifecycle-safe reapproval, invalidation and recovery rules; do not use ordinary Scope Publish to rewrite active execution.

Record the classification for **every proposed work item**, including rejected candidates, with an explicit outcome: `IMPLEMENTATION`, `ACCEPTANCE/VERIFICATION`, `RELEASE/DEPLOYMENT`, `INVESTIGATION/DECISION`, or `ALREADY SATISFIED`. These are **planning categories, not provider labels, runtime result enums or a new state system**. Only `IMPLEMENTATION` may be published into a code-backed self-delivery lifecycle. If any proposed Issue cannot pass the five checks, the affected bound Plan is **not `PLAN_READY`** for that enrollment; do not fix it by fabricating a Candidate. Preserve the real verification/release obligation in the existing accountable stage so it does not disappear.

## Modes, authority and boundaries

**Plan**, **Publish** and **Audit** are mutually exclusive modes. Plan and Audit are strictly read-only; Publish is a separately authorized invocation that creates only the approved raw work and native dependencies, and then verifies provider read-back. Scope does not select executors, grant work eligibility or produce Shape, Delivery, Acceptance or completion proofs. Role and permission limits apply equally to people and Agents.

Read the project's **current normative authority** (Proposal, product specification or authorized decisions), current repositories/tests/releases/Issues/PRs, the **intended delivery policy**, the **delivery mechanism actually installed for the project**, and the issue provider's supported operations. Keep normative repository ownership distinct from observed code location; record drift, never silently change ownership. A delivery engine being developed as the product is not necessarily the currently installed executor of this portfolio.

- **Authority is read-only and decision-specific.** Check the document's explicit decision/approval records **and current Owner authorization** for each binding clause, with exact anchors and affected work. A document labeled draft does **not** make every explicit approved decision undecided; conversely, approval of some clauses does **not** approve the whole document. Before blocking, identify the precise unapproved or contradictory clause, the behavior/Issues it affects, **why existing approvals are insufficient**, and the exact decision needed. Do not invent a global document-approval prerequisite, change normative authority, infer approval from old code/history, or ask about decisions already settled by attributable evidence. Return `AUTHORITY_UPDATE_REQUIRED` only where changing a binding product decision is necessary; otherwise classify the actual unresolved requirement within its affected scope.
- **Invocation boundary:** Bind a whole project or an explicitly approved requirement slice; cover every obligation in the boundary and all material cross-cutting security, compatibility, integration, documentation, release and operational obligations that govern it. Reference unrelated future work without expanding the bound scope. A slice cannot claim whole-product completeness.
- **Protected work:** Raw publication is not a grant or freeze. Changes to already frozen, authorized, shaped, executing, delivered or closed Issues (including metadata, assignments and native dependencies) need the project's separately authorized invalidation/reapproval/recovery process first. A Scope Plan approval does not provide it. No actor may silently assign/reorder executors or trigger delivery through raw issue creation. An authorized publisher, not Shape Author/Validator, applies approved formal Shape updates under the delivery policy.
- **Scope and Shape separation:** Scope may use Shape's **bounded read-only Investigation** for evidence about a prospective work item, interface, ownership or prerequisite, without initiating formal Shape. Findings are advisory; Scope alone determines portfolio split, chosen planning route, Issue creation, verification ownership and dependency design. Shape later works on **one existing raw Scope Issue**, within its frozen boundary, through the project's independent validator and trusted publication flow; it owns detailed Acceptance Criteria, not portfolio redesign. If the proposed work cannot stay in Scope, Shape reports the exact conflict for authorized replanning, not a self-created sibling Issue or a broadened proof requirement.
- **Reusable contract:** Do not hardcode a project's repositories, issue IDs, platforms, commands, permissions, labels, roles, versions or product-specific policies in this Skill. Resolve them from the current authority, provider and runtime. The approximately **1,000 meaningful first-party LOC** target below is a reusable planning guideline, not a product requirement.

## Plan: establish coverage before drafting Issues

1. **Inventory authority by decision, not document label:** For each bound requirement compare its exact anchor with in-document approvals and current Owner authorization; record **approved**, **specifically undecided/contradictory**, deferred or excluded, the affected behavior/Issues, normative repository owner, existing implementation/evidence, planned work and product-level proof. An ambiguous binding decision needs evidence-led investigation and an exact question; a draft heading alone is not evidence of a gap or a missing blanket approval. Source-project completion never proves target-project delivery.
2. **Inspect reality and deduplicate:** Review relevant open **and closed** Issues, code, tests, PRs, published sources/releases, provider contracts, and the reusable flows or upstream interfaces each candidate Issue actually invokes. Trace inherited privilege, environment, evidence and success conditions through those shared paths; a shared implementation does **not** mean every caller must satisfy the same privileged observation or has the same completion status. Reuse legitimate work. If existing Issues are deliberately not inspected, mark deduplication `UNVERIFIED` and **publication readiness blocked** until checked, not technology infeasible or falsely duplicate-free.
3. **Classify each candidate before allocating its owner; own every implementable outcome and the single bootstrap:** Choose one normative owning repository and coherent deliverable per Issue; do not duplicate cross-repository core logic. **For each genuinely empty project, create exactly one minimal initialization root Issue** owning the shared directory/package configuration, tooling and dependency management and lockfile, necessary build/typecheck/test entry points, common settings and initial module boundaries. All other work for that project must depend **directly or transitively** on completion of this baseline before changing shared setup; no parallel root may initialize the same project. A website, testing or research subdirectory does not automatically create an independent project or justify a conflicting second initializer. Independently empty projects each have their own single root; an existing usable baseline is reused **without** a new bootstrap Issue. Keep the bootstrap free of feature delivery, formal release and E2E; once complete, independent feature work may run in parallel, without an all-shaped barrier. For cross-platform work, choose a grounded coding route with applicable capability/tool detection, host/guest separation, service/login/cleanup and denial/unknown behavior. Coding for a target OS does not require a planner or coding Agent on that OS.
4. **Bound work:** Target roughly 1,000 lines or fewer of meaningful maintained first-party changes per implementation Issue, including copied/ported adaptations, tests, workflows, configuration and nontrivial refactors (not merely net added lines). Give an estimate range and confidence. If larger, seek separable outcomes; if not safely divisible, record the reason and its explicit exception within the Owner-approved Plan. Use appropriate alternative effort units for **maintained product documentation**. Release/evidence work stays in its actual non-delivery responsibility, not an implementation estimate. Never drop necessary tests to meet the budget.
5. **Resolve actual operation and inherited-permission paths:** Consult official provider/API/OS contracts and existing code before changing a candidate Issue. For each required operation, including those inherited from reused helpers or workflows, identify the acting identity, environment, permitted API/operation, required permission, input and source of evidence, and distinct success/failure/unknown outcomes. Do not impose a privileged Owner/controller listing check on an ordinary member simply because both use a common registration helper; distinguish successful permitted setup, fresh bounded local observation, uncertain remote state and separately authorized dispatch eligibility. An access-denied management lookup is not automatically a failed setup, nor is local success remote authorization. Prefer a lawful existing path over inventing a new API or research Issue. Shape owns detailed implementation/testing mechanics, not deciding away the approved permission boundary.
6. **Allocate whole scenarios, not merely test fragments:** Identify locally complete implementation evidence and every product-mandated real OS/architecture, security, authentication, provider, installation-to-delivery, deployment and release journey. An accountable existing acceptance/release/provider process must cover each required **complete journey and outcome**; **do not create a standalone code-backed self-delivery Issue just to name its verifier**. Implementation Issue Bodies identify relevant verification ownership, inputs and support-claim limits, while official E2E and release evidence remains with the legitimate actual executor. Separate installation, registration, lifecycle and reporting trackers are not proof that someone has run the end-to-end path. Verify actual ordered inputs, authentication and environment boundaries, handoffs, failure cases, retained provider evidence and the terminal checker; a report compiler is not a real scenario executor. A documentation Issue that only describes proven steps cannot silently be required to rerun them. Missing later E2E resources affect the actual verifier's readiness, not locally testable upstream implementation.

### One producer → consumer → verification → completion review

For every material required interface, artifact, release or evidence obligation, **trace both forward from the producer and backward from the consumer/required product claim**, consulting both complete work boundaries. Use one review rather than independent overlapping matrices:

1. **Producer actually owns the output.** Identify the implementation/configuration producer and, where needed, the **separately authorized release/publishing operator or existing workflow**. An installer, upgrade command, build/test runner or source-code implementer does **not automatically publish a formal release**. If a consumer requires an *already released* CLI/Action/library, establish the actual publication owner, availability, source pin, approval and read-back plan **without inventing a separate AI self-delivery Issue for the act of publishing**. Allocate missing release work to the already authorized release process; if the product lacks such a process, report the exact release-readiness/authority gap. A referenced release does not exist merely because a consumer requests it.
2. **Consumer can obtain the correct maturity.** Record the concrete file/export/API/command/configuration, intended location, main inputs/outputs/error states or permitted local contract, producer/consumer, retrieval/build/import/call method, needed-by stage and necessary read permissions. Prefer the current accessible source and usable interface. Do not introduce a hash or fixed version as a work prerequisite. If a design genuinely needs an exception, explain the concrete need and ask the Owner before adopting it. A future file may be planned if its producer owns it; do not claim an unpublished release or unavailable package exists. Require candidate build, formal published release or actual measured result **only when the consumer really needs that maturity**. No generic “versioned artifact” or extra handoff package substitutes for a usable contract.
3. **Verification is reciprocal and end-to-end accountable.** For every required scenario, compare the implementation Body's handoff with the named verifier's **Goal, Scope and own completion**. Ensure one legitimate executor explicitly owns the complete mandated path where required, not merely an unconnected union of step tests; its producer inputs and maturity arrive in time, and a separate accountable checker consumes the real result for the required release/support/completion claim. A compiler of existing results is not an executor; **nor does the executor need a new implementation Issue when its work has no maintained source outcome**. Distinguish locally accepted implementation, actually performed E2E and formal support claims. Missing later test resources are verifier readiness, not prior module failure.
4. **Re-read the real Issue behavior and single completion boundary.** Compare **every sentence** of Goal, Scope, operations (including reused-flow prerequisites), outputs, verification targets, mandatory proof stages, artifacts/hooks, dependencies, exclusions and referenced counterpart Bodies. Name the required actor/environment/permission and meaning of success, denial and unknown **with an exact body or authoritative-source anchor**. Implementation completes through necessary maintained changes plus local/contract/negative evidence; external scenario verification and formal release complete through their existing authorized evidence/publication mechanisms, **not through a fictitious code-backed Issue**. Real product documentation can be implemented as maintained source; an evidence-only report does not become product code. Flag any contradictory clause (for example, excluding E2E while requiring a live Quick Start as document acceptance) and any alternatives such as “code **or** test plan **or** real proof **or** Not Ready.” Missing environment is a pending verification, never a completed test. Do not create a fictitious proof artifact/hook or import downstream E2E into module completion. Only real repository/runtime obligations apply.
5. **Check order and closure.** Ensure the output exists or its planned producer will supply it **before the consumer needs it**. In particular, a final compatibility report cannot block the initial release whose execution creates its evidence. Trace every binding outcome to an actual producing work item, its necessary users, a mandated real verifier when applicable, and a checkable terminal completion/support decision; intermediate consumers are fine. Flag the **first broken link** and impacted work instead of accepting filled-in cells, a closed research ticket or an acyclic graph as proof of deliverability.

**Correction loop, not checkbox approval:** After drafting, re-read **every complete proposed Body and every necessary upstream, reused-flow and verifier Body** as an execution story. In the final Issue Body, check every claim of existing capability against the current code or provider interface. If the Issue owns a missing capability, state that it will implement it and name the components it can reuse. For each binding operation, completion outcome and product scenario, cite the exact statement or provider/code evidence supporting the actor, permission, outcome, producer, verifier and terminal checker; generic phrases such as “least privilege,” “read back” or “later E2E” are insufficient. Record the first contradiction and affected transitive consumers. Verify authoritative docs/current code first, then **correct only the proposed draft Bodies, responsibilities and planned edges that the current Plan may revise** without inventing an interface, research ticket or earlier environment gate. Repeat the same check on the corrected work and impacted neighbors; report `RESOLVED` only after both sides and the consumer claim agree. If a necessary source is inaccessible or an existing protected Body cannot lawfully be edited, record `UNRESOLVED` with affected items and the required separately authorized action. Such a bound plan cannot be `PLAN_READY` or be described as wholly passing. Independent complete slices may be assessed separately, never as a waiver for the failed bound plan.

### Dependency and risk review

- **A verification/release milestone is not automatically a native implementation dependency.** An implementation consumer may require a truly available released artifact or mandated proof, but trace that need to the **real version, official release, existing CI/acceptance or provider result** and its lawful owner. Do not add a `Blocked by` edge to an evidence-only tracker purely to preserve the planning graph. When removing an improperly enrolled tracker, **re-evaluate each downstream native edge separately** through the authorized mutation/recovery path; neither blindly delete an edge nor treat the tracker as delivered.
- Before `PLAN_READY`, inspect every **proposed self-delivery Issue** for meaningful maintained change, grounded existing-interface assumptions and an actually compatible installed runtime. Record `NOT SELF-DELIVERY` for any verification, release, experiment or administrative task rather than trying to shoehorn it into a PR/Candidate.

- A hard edge is justified only by the **specific not-yet-satisfied output or policy-required proof** the downstream work cannot begin or finish without, including source maturity and availability. It is not a roadmap priority or preference to serialize. Examine direct **and transitive** dependencies; do not make an upstream module wait for real E2E proof generated only after its consumers exist.
- Validate stable identities, missing/external predecessors, cycles, consumer/source maturity, issue-provider native-relationship support, and actual installed execution policy's recognized completion proofs. For an empty project's planned graph, ensure **exactly one minimal bootstrap root** and a direct/transitive dependency path from every other Issue in that project to it; prevent competing initialization work without turning the post-bootstrap project into a global serial chain. For an already initialized project, do not invent a root to satisfy this check. Graph membership in a plan is not runtime eligibility. Evaluate every suspected transitive/redundant edge **individually** for independent contractual/policy necessity; do not bulk-delete by count. Identify independently parallelizable post-bootstrap work and semantic artifact-order cycles.
- For product-critical assumptions, identify grounding, alternatives, downstream impact and later evidence that would disprove the selected route. A real contradiction with binding requirements or an undecided product behavior must return to the separate authority process. Ordinary implementation uncertainties stay in the chosen Issue; an unavailable external test resource stays with the real verifier. Do not add a research/spike Issue merely to test feasibility as a substitute for coding.
- Before a large freeze/authorization, report the **actual current delivery engine's** ability (verified, unverified or unsupported) to safely handle partial Scope changes, native edge updates, evidence invalidation, authorization migration and restart/recovery. Missing a convenient partial migration feature does not alone block Plan/Publish, but protected change still requires the real recovery process.

## Raw Issue contract and Shape handoff

Each **complete raw Issue Body** should be readable without reconstructing the portfolio tables. Adapt these elements to the project's existing conventions, without embedding unrelated project-wide security boilerplate:

- **Outcome and ownership:** current gap, exact binding authority anchors and decision-specific approval status, observable result, one normative owning repository, included/excluded work and adjacent interfaces. If this is the **sole bootstrap** for an empty project, state its minimal shared baseline and exclude features, publication and E2E; other project work cites this baseline rather than separately initializing it.
- **Selected implementation route:** relevant grounded candidates and limitations (without inventing extra choices), **one selected route and rationale**, source facts versus assumptions, essential platform branches/identity-permission boundaries, and the planned maintained code/configuration/documentation. State which existing components the Issue will reuse, which capabilities it will add, and which capabilities another Issue must provide first.
- **Inputs and handoff:** actual/planned upstream interface/source or formal published artifact **at the maturity needed**, producer/consumer and acquisition/build/use method, planned pin and required-by stage; no invented archives or needlessly repeated upstream tests. Identify required native dependencies and why each exists.
- **Own completion:** a **single substantive maintained development output** and its proportionate local/contract/negative checks, with applicable artifact/hook obligations based on real configuration. Separately name later E2E/security/installation/release evidence and its actual authorized executor **outside the code-backed Issue completion**. Never turn a standalone test, release, audit or evidence report into a Candidate to satisfy the delivery engine.
- **Later proof and route outcomes:** name the true later scenario executor and downstream evidence/check consumer for each applicable real OS/auth/security/integration/support claim, with readiness separately noted. Distinguish (a) repair a programming defect in this Issue, (b) report a host/login/download/provider environment blockage without declaring route failure, and (c) evidence demonstrating the selected **route itself** violates the binding requirement. For (c), propose a separately approved **two-way linked alternative Issue** carrying the original decision, failed evidence, attempted fixes, candidates and replacement rationale; never auto-open, rewrite or close protected work.
- **Estimate and disclosure:** meaningful-change range/exception, any specific residual risks, and public-safe references only. Do not copy private source, secrets, fixtures, credentials, internal logs or confidential evidence into public Issues simply because the planner can read them.

**Scope → Shape handoff** after Publish preserves the verified repository/Issue stable identity, current provider-read Issue Body and source location, normative authority anchors, read-back native prerequisites, selected approach, bounded local-vs-later proof allocation, usable producer inputs, 1,000-line assessment and any dated read-only Investigation. The handoff is **not** a trusted Core freeze/grant, formally validated Shape, completion receipt or permission for Shape to widen the Issue. A formal Shape Author/independent Validator/trusted publisher must independently check current authority and the original frozen Scope according to the actual runtime policy. If Shape discovers an invalid split, absent source or wrongly allocated proof, return the exact finding to Scope Plan/Audit; do not silently invent more mandatory artifacts, downstream E2E or sibling Issues.

## Plan outputs and verdict

Provide a **concrete full proposed portfolio**, not only a positive summary:

1. **Bound authority and coverage:** per-decision approval/undecided/deferred status grounded in exact clauses, document approval records and Owner authorization. For each unresolved decision identify **the specific conflicting/unapproved text, affected Issues/behavior, insufficient evidence and decision required**; do not substitute a document-wide draft status. Report requirement-to-Issue coverage, observed vs. normative ownership, actually evidenced prior completion, inspected revisions and unavailable access.
2. **Complete raw Issue register:** planned IDs, full proposed Bodies, selected routes and assumptions, estimates/exceptions, exact work boundaries and evidence allocation; actual provider Issue IDs are not required before Publish.
3. **Single responsibility trace:** for each necessary produced API/code/package/release/test evidence, its actual producer/packager, required version maturity/acquisition/timing and consuming work; each real scenario executor and final evidence/completion checker, reconciled against both complete Bodies. Identify the first broken link, required correction and transitive impact.
4. **Dependency manifest:** justified producer → consumer hard edges with intended native-provider/policy compatibility, Mermaid DAG, artifact order and individually reviewed apparent transitive redundancies. For each empty project show its **single minimal initialization root**, every other Issue's direct/transitive path to it, and independent parallel branches after baseline completion; for already initialized projects cite the usable baseline instead. Planned references are not actual provider-native relationships.
5. **Publication plan and risk:** full approved-to-be-written Issue bodies/metadata/edges, disclosure check, safe raw-creation triggers, intended durable journal and reconciliation method; critical route risks, future E2E resource readiness, and actual engine change/reapproval limits. List necessary Owner decisions and protected-work constraints explicitly.

**Pre-verdict evidence record:** Cite exact **re-read Body/authority clauses**, changed draft passages and freshly **compared** upstream/downstream responsibility and dependency design, including the bootstrap uniqueness/path check where applicable. Distinguish four evidence levels in the report: **(1) text reread/compared, (2) design/dependency examined, (3) tests actually executed with command/result, (4) real-environment results actually observed with source/time**. Mark absent levels **not executed/not observed**. Static review may support a **planning-design** verdict, but must never be described as a passed test, executed scenario or proven real-platform behavior. State open gaps and the next authorized actor.

**Plan verdict:** `PLAN_READY` only when **every proposed code-backed self-delivery Issue passes the mandatory work-type and feasibility gate**, and the **post-correction design** has text-anchored binding decisions, legal operations, substantive maintained completion criteria, real producer/verifier/check ownership, valid ownership/dependencies and, for each empty project, one noncompeting minimal bootstrap root with all other work downstream. An unresolved specific approval/authority conflict, absent necessary owner/output, competing initializers, contradictory completion, unauthorized operation or invalid dependency yields `PLAN_BLOCKED` for its affected bound plan, naming its precise clause and impacted work. Use `AUTHORITY_UPDATE_REQUIRED` when the controlling product decision must change, **not** merely because the document is called draft. Never imply that this design verdict means a test was run. Owner Publish approval, journal, provider Issue IDs/native read-back or later E2E environments are **separate readiness**, not design failures.

Report **separate readiness**: (a) Plan design verdict, (b) existing-work deduplication `VERIFIED`/`UNVERIFIED`, (c) Publish `AVAILABLE`/`BLOCKED`/`UNVERIFIED` including approval, write access, journal and read-back prerequisites, and (d) each named later verifier's environment readiness and affected support claim. Uninspected existing Issues prevent claiming deduplication or actual Publish readiness, but are not automatically an implementation-technology defect. Plan readiness does not authorize writes or certify delivery.

## Publish: authorized mutation and recovery

Publish runs **only after separate explicit Owner approval of the complete concrete manifest**, including authority revision, full raw bodies, repositories, metadata, exact native edges and every proposed change. Before first mutation, independently refresh authority, existing issue inventory and duplicate/identity checks, **work-type eligibility against the actual installed Candidate contract**, owning repo and permissions, selected-route and proof-boundary consistency, native edges, protected-work eligibility and disclosure safety. Replan and reapprove if those material facts or the approved write set change. No unapproved assignment/metadata alteration or implicit execution enrollment. Actual provider permissions and a **writable, durable, recoverable journal** are hard Publish preflight requirements, not Plan validity conditions. If impossible before any write, return `PUBLICATION_BLOCKED` or `REPLAN_REQUIRED` without claiming partial success.

For each authorized Issue/metadata/native-dependency operation:

1. Persist a **write-ahead intent** before invoking the provider, binding the approved manifest, target, operation, expected identity/body/edge and stable correlation key. Do not proceed if the journal cannot survive restart or distinguish retries.
2. Perform only approved writes on eligible raw work; persist responses and independently read back actual stable repository/Issue identity, exact Body, approved metadata and **both native dependency directions**. Real native provider relationships are required wherever the project delivery policy uses them; Markdown checklists do not substitute.
3. Reconcile timeouts, lost responses, partial publication or concurrent publishers against persisted intents and fresh provider reads **before** any retry. Unknown or ambiguous outcome stops the affected operation; never blindly duplicate, auto-rollback, conceal drift, or overwrite protected work. Remediation needs a separately reviewed/approved new Publish after applicable lifecycle recovery.
4. Create the public-safe Scope → Shape handoff from the **provider-read exact raw baseline**, identity and native graph. Keep necessary private evidence in access-controlled storage, not lower-trust Issue Bodies.

Return `PUBLISHED` only when every approved operation and handoff is fully reconciled by read-back; return `PARTIAL_PUBLICATION` when a write occurred but completion is unknown or incomplete. Raw publication creates neither Owner Grant nor a shaped, accepted, merged or completed Issue. The trusted delivery mechanism independently applies every later stage and permission gate.

## Audit: read-only reconciliation

Use **the same mandatory work-type/feasibility gate, per-decision authority, actual-Body, inherited-flow, complete-journey, bootstrap and responsibility-chain design checks** as Plan against observed Issues, native edges, histories, releases and source. Flag existing verification/release trackers wrongly enrolled for code-backed delivery, and trace their downstream dependencies without changing provider state during Audit. Check whether a greenfield project has exactly one initializer and all sibling work depends on its baseline, or reuse a pre-existing verified baseline; do not impose post-bootstrap serial execution. Cite observed clauses, compare required producers/permissions/completion/verification and independently inspect actual provider state only when accessible. Audit is **read-only**: propose corrections and protected-work handoff without applying Plan's draft edits. Distinguish **static text review**, **design/graph checking**, **actually executed tests**, and **observed live-provider/E2E evidence** in any claimed result; an unrun test or unseen real environment is never reported as passing. An authorized Shape Body update does not by itself mean Scope drift.

Return `AUDIT_PASS` only for the bound portfolio supported by the observations and disclosed limitations; return `AUDIT_FAILED` with the precise failing Issues, responsible missing outputs, incorrect verifier claims, native graph or handoff mismatches, evidence/authority gaps and repair ownership. Unknown provider/runtime proof is not a manufactured completion. **Audit never creates, edits, relabels, reassigns, closes or repairs an Issue.** Corrections require an independently approved Publish or the protected lifecycle's separate authorization/recovery process.

## Report and fixed verdicts

| Mode | Verdicts |
| --- | --- |
| Plan | `PLAN_READY`, `PLAN_BLOCKED`, `AUTHORITY_UPDATE_REQUIRED` |
| Publish | `PUBLISHED`, `PARTIAL_PUBLICATION`, `PUBLICATION_BLOCKED`, `REPLAN_REQUIRED` |
| Audit | `AUDIT_PASS`, `AUDIT_FAILED` |

Use **one verdict for the active mode**. `OWNERSHIP_UNRESOLVED` is a finding, not another verdict. Report bound scope, current authority and code revisions, inspected Bodies, **specific undecided clause → insufficient approval evidence → affected behavior/work → decision needed**, each correction and static post-correction review, remaining blockers and downstream impact, ownership/graph including bootstrap dependencies, and distinct publication/deduplication/later-test readiness. A planning `PLAN_READY`/`AUDIT_PASS` is not a claim of implemented, tested or supported product behavior.
